# Blazor Blueprint competitive review and roadmap

Research date: **16 September 2026**. Bb source baseline: local branch `v4`, commit `917e9483c6fd666a95af5163dc3559ef269e533d`, including the capabilities described in the checkout's unreleased changelog. Planning audience: business applications and SaaS, with enterprise data workflows as the next expansion area.

**Recommendation:** Make Bb an exceptionally dependable, customizable Blazor toolkit for business applications. Its component breadth is already substantial. The highest-value work is proving reliability, extending the existing grid, finishing common application workflows, and improving design-system controls. Matching every specialized product in a commercial suite would require a much larger, separately funded program.

This is a source-and-documentation assessment, not a performance benchmark or accessibility certification. Competitor capabilities below are documented by their maintainers; they were not exercised in identical applications. Bb features were checked against implementation and public API where possible. A feature in this checkout is not necessarily in the latest stable NuGet package. Estimates and priorities are planning judgments, not measured demand or delivery commitments.

**What the competitive set tells us**

Ten libraries were reviewed. The first eight cover common open-source and commercial alternatives; NeoUI tests Bb's closest design proposition, and HAVIT tests onboarding and business-application ergonomics. This is a representative comparison, not a census of every Blazor package. ComponentOne, Infragistics, BootstrapBlazor, Blazor Bootstrap, and specialist chart/editor packages merit a second procurement-oriented pass if their particular workloads become priorities.

**Bb's starting position is stronger than a missing-component list suggests**

The [README](../../README.md) advertises 112 styled components, 28 primitives and 11 chart types. These counts include families and convenience wrappers; other vendors count differently. They are not a normalized coverage metric.

Bb already has the following foundations:

- A styled/headless split, packaged CSS, shadcn-style theme variables, dark mode, a theme service and switcher. The current v4 work isolates utility classes with `bb:` and a separate cascade layer. See [theming](../../THEMING.md) and [v4 migration](../../V4-MIGRATION-GUIDE.md).
- An extensive DataGrid: multi-sort, column filters and search, nested grouping and aggregates, hierarchy and lazy children, row virtualization and asynchronous providers, selection, detail rows, pinned/reordered/resized/hidden columns, state, **row editing**, and **CSV export**. See [grid implementation](../../src/BlazorBlueprint.Components/Components/DataGrid/BbDataGrid.razor.cs).
- Form-field wrappers, EditContext-aware input validation, dynamic schema forms, a form wizard, filters, date/time inputs, masked/numeric/currency inputs and multi-selection. See [input integration](../../src/BlazorBlueprint.Components/Components/Input/BbInput.razor.cs) and [dynamic forms](../../src/BlazorBlueprint.Components/Components/DynamicForm/BbDynamicForm.razor.cs).
- ECharts-backed composable charts, dashboard layout, docking, tree views, drag-and-drop primitives, rich text and Markdown editors, and an event calendar. These are existing investments to deepen.
- A localization interface and English defaults, culture-aware formatting, and some explicit RTL behavior. See [localizer](../../src/BlazorBlueprint.Components/Localization/IBbLocalizer.cs), [localization guide](../../demos/BlazorBlueprint.Demo.Shared/Pages/Guides/LocalizationGuide.razor), and [keyboard utility](../../src/BlazorBlueprint.Primitives/Utilities/KeyboardNavigator.cs).
- Server, WASM and Auto demo hosts, API snapshots, targeted behavior/convention/performance tests, and a JavaScript drag-update test. See [tests](../../tests/BlazorBlueprint.Tests), [JS tests](../../tests/js/drag-updates.test.mjs), and [render-mode guide](../../demos/BlazorBlueprint.Demo.Shared/Pages/Guides/RenderModesGuide.razor).
- Existing application blueprints and AI-facing documentation. The [public site](https://blazorblueprintui.com/) exposes reusable pages; [llms.txt](https://blazorblueprintui.com/llms.txt) exposes an indexed documentation set. A separate local [Pro tree](../../pro/README.md) contains additional blueprint work; its release readiness and claimed SaaS/AI features were not audited here.

The [August grid plan](../../devkit/docs/plans/2026-08-27-datagrid-enhancements.md) described editing/export as absent then. That is no longer an accurate baseline: row editing, CSV export and nested grouping are now implemented. Older plans should be reconciled with source before becoming new issues.

**Immediate corrections and low-cost improvements**

The public [home page](https://blazorblueprintui.com/) currently says 115+ components and 11 MCP tools; the checkout README says 112 components and 15 tools. The public [AI index](https://blazorblueprintui.com/llms.txt) identifies library version 3 and a July 2 update, whereas the checkout is v4 work. These may describe different releases, but the distinction is not apparent enough. Generate counts from a defined catalog and let both humans and tools select a package version. Do not simply overwrite stable docs with preview APIs.

Remove or qualify exclusivity claims about shadcn theme compatibility: NeoUI documents the same broad capability. Treat MCP as an expected developer aid, because Radzen, Syncfusion and Blazorise also document AI/MCP tooling. A dated historical claim such as being first would require historical evidence; current uniqueness is not established. [NeoUI](https://github.com/jimmyps/blazor-shadcn-ui), [Radzen MCP](https://www.radzen.com/blazor-mcp/documentation), [Syncfusion MCP overview](https://www.syncfusion.com/blazor-components), [Blazorise usage](https://blazorise.com/docs/usage).

Reconcile internal documentation as well. The [chart README](../../src/BlazorBlueprint.Components/Components/Chart/README.md) still contains unprefixed component examples, while the current [composite chart API](../../src/BlazorBlueprint.Components/Components/Chart/Types/BbChart.cs) uses `Bb` names. Compile maintained examples against their declared version rather than relying solely on manual review.

Publish runtime compatibility evidence promptly. Microsoft's support calendar puts **.NET 8 end of support on November 10, 2026**; .NET 10 is the current LTS line. Testing net10 consumer hosts is urgent. Changing every library target is a separate compatibility decision: a net8 library can be usable from a net10 application. Retain compatible consumers where practical, and choose multi-targeting or a major-version minimum based on actual requirements. [Microsoft support policy](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core).

**Implementation approach for the largest gaps**

**Grid: extend the existing implementation incrementally.** Keep the current row mode and existing providers. Define cell-edit lifecycle, navigation and validation before adding an enum value. The row snapshot currently captures writable property values, including reference values; it is not a deep transactional copy. Provide an explicit edit-model/clone strategy for nested objects and a predictable save/reject/cancel contract before building batch editing on top. See [snapshot implementation](../../src/BlazorBlueprint.Primitives/Primitives/DataGrid/DataGridRowSnapshot.cs).

Required acceptance scenarios: invalid cells retain focus and errors; Escape restores the intended edit scope; server rejection preserves typing; sorting/filtering does not silently discard changes; scrolling an edited virtual row has a documented outcome; concurrent save responses cannot overwrite newer edits; stable ItemKey survives reload. Add create/delete and popup-form recipes using current Dialog/DynamicForm pieces before deciding whether they require new grid APIs.

**Export: fix remote completeness before adding formats.** Introduce an explicit export-data contract that receives the active sort/filter/search/group descriptors plus cancellation. It must distinguish current page, selected rows and all filtered records. Reuse a canonical column/value projection so on-screen values and export values agree. Stream or page large exports through an application endpoint; avoid sending an unbounded dataset through a Blazor Server circuit. Keep XLSX serialization in an optional package/adapter. Validate numbers/dates, hidden and template columns, Unicode, quoting, and spreadsheet formula-like content. PDF requires an explicit printable layout; it should not be assumed equivalent to serializing table data.

**Remote data: prove combinations.** Retain ItemsProvider and GroupedItemsProvider. Supply examples against an actual database and HTTP endpoint, exercising cancellation and failures. State which combinations remain client-side and their expected scale. The current Queryable optimization is useful but not universal: search/grouping/hierarchy/virtualization can take different paths. Only implement column virtualization if a measured wide-table workload warrants its complexity, including pinned columns, resizing, keyboard access and assistive technology.

**Scheduler: treat it as a domain feature.** Preserve EventCalendar for lightweight display; a separate component avoids making a simple calendar carry scheduling state. First establish event identity, visible-range loading, local time versus stored instant, time zone and invalid/ambiguous DST policies. Deliver time-slot views and CRUD interactions, including keyboard alternatives to dragging. Then resources, overlap policies and recurrence with exceptions. Validate single-occurrence versus series edits, all-day events and cross-zone display. A mature recurrence implementation may be an independently evaluated dependency; do not improvise recurrence arithmetic inside UI code.

**Design system: make customization consistent.** Extend theme tokens and scoped defaults for density, typography, spacing and component parts. Keep existing Class overrides and prebuilt CSS working. Ensure a nested theme/density scope reaches content rendered through portals. Begin with three tested profiles — default, compact and comfortable — and validate focus indicators, touch targets, clipping and contrast in light/dark/RTL. Broader preset catalogs can follow demand. A Figma/token export is useful only if maintained from the same source.

**Localization: complete the contract already present.** Inventory all UI and accessibility strings, including inline markup, errors and newly added editor actions. Use one rule for language/culture versus layout direction; test a RTL container inside an English-language app. Convert incidental physical spacing to logical spacing where appropriate, without changing intentional physical placement such as docking sides. Start translation packs with reviewed, named maintainers and automated key-completeness checks.

**File and task workflows: compose before promoting.** Build TreeSelect from the existing tree/overlay mechanisms. Prototype a file-browser recipe and Kanban/task board from TreeView, DataView, DataGrid and Sortable; evaluate keyboard, touch, loading and persistence behavior. Promote reusable behavior into components only after multiple screens need it. Keep storage authentication/authorization in the consuming application and expose capabilities/callbacks at the UI boundary.

**AI and docs: measure correctness.** Add a version to every returned API/example record, compile selected generated tasks against that version, and test setup as well as component markup. Include a CRUD page, filtered grid, nested dialog/select, validated form and themed dashboard. This develops Bb's existing MCP investment without confusing model marketing with reliable developer outcomes. The MCP implementation lives outside the inspected core scope; its tool behavior still needs a dedicated audit.

**Sequenced delivery plan**

The stages below are ordered by dependency and adoption impact. Effort ranges are initial estimates in **focused engineer-weeks**, including implementation, review, tests, examples and docs, assuming an experienced maintainer who knows Bb. They exclude routine support load and specialist procurement/audits. They are not calendar durations, and estimates should be revised after small design spikes.

| Stage | Scope and dependency | Initial effort | Release gate |
|---|---|---|---|
| **A — Establish a trustworthy baseline** | G01–G04/G16: release manifest, versioned docs, net10 consumer smoke apps, PR build/test checks, initial browser/accessibility scenarios. First establish what stable and preview actually ship. | **5–8 weeks** for the initial baseline, not a whole-library accessibility audit. | Examples match declared versions; all advertised interactive hosts have passing package-based smoke tests; highest-use overlays/forms/grid journeys run in CI; known limitations are published. |
| **B — Complete common data workflows** | G05–G07: export provider contract, XLSX adapter, cell-edit lifecycle and implementation, provider recipes, combination tests. Depends on A's browser harness. Batch/clipboard and column virtualization remain separate follow-ups. | **10–16 weeks**. | CRUD and full-result export reference app works with remote paging, validation errors, cancellation and server rejection; no hidden client-side full fetch in the tested paged scenario. |
| **C — Strengthen custom design systems** | G09/G10/G16: direction/locale completeness for core flows, density/defaults/portal propagation, template and migration improvements. Depends on A. Can overlap B with separate capacity. | **6–10 weeks** for initial profiles and representative locales. | The same reference app passes visual/keyboard scenarios in light/dark, compact/comfortable and LTR/RTL, with reusable configuration. |
| **D — Add the next demanded workflow** | Choose G08 scheduling or G11/G12 selection/upload based on adoption evidence. Do not launch every candidate simultaneously. Depends on A and the relevant form/data contracts. | **6–10 weeks** for a limited Scheduler v1; **another 8–16+** for robust resources/recurrence/time-zone depth. Alternatively **4–8** for an initial TreeSelect/upload tranche. | Publish exactly which workflow is supported; scenarios include errors, accessibility and persistence, not only a happy-path demo. |
| **E — Specialist enterprise expansion** | G13–G15 plus advanced grid follow-ups. Fund separately after validating workloads and maintenance ownership. | Discovery estimates required; no credible aggregate estimate from this review. | Demand-backed decision to build, integrate or defer each product; explicit package, license and support boundaries. |

Stages A–C total approximately **21–34 focused engineer-weeks**. With one maintainer, support and release work will make elapsed delivery materially longer. “Parity with all commercial suites in 90 days” would not be a responsible promise.

A realistic **first 90 days for one experienced full-time maintainer** provides about eight focused engineer-weeks if roughly 25% of time is reserved for support/regressions and 15% for maintenance/documentation outside feature delivery. Commit to Stage A. Use any remaining capacity for the remote-export scope correction and contract spike; schedule XLSX and cell editing after that baseline, rather than promising both within the quarter. With two maintainers, put the second on design/RTL after the baseline, rather than splitting ownership of the grid internals.

These are proposed success measures, not current results:

For comparative benchmarks, build equivalent screens with identical data, hosting, hardware, browsers and network conditions. Separate framework overhead from component cost, feature depth from speed, and initial download from warm interaction. Publish harnesses and full results, including cases where another library wins. No claim that Bb is presently faster, smaller or more accessible follows from this review.

**Investment boundaries**

Keep fundamental accessibility, correctness, localization hooks and supported-render-mode behavior in the core quality standard. Optional packages are appropriate for heavyweight exports, specialist visualization, document integrations and adapters. Build on the existing free and Pro blueprints before starting a competing scaffold catalog.

Defer native spreadsheet/DOCX engines, full reporting designers, sophisticated Gantt/diagram systems and a visual IDE until multiple committed users have concrete requirements and an owner can fund ongoing maintenance. A theme-compatible integration can satisfy an application requirement without claiming native component parity. Packaging integrations does not remove upstream licensing or support constraints.

If the target shifts to enterprise data applications, promote batch editing, column virtualization, scheduler resources/recurrence and pivot discovery. If it shifts to custom design systems, promote headless coverage, scoped tokens, density, RTL and design-tool integration. For the default business/SaaS target, start with the ten-item backlog above and reassess demand after the first reference application ships.
